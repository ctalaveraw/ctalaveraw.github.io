### Symptoms

Storage operations on the NanoPi R5C became unresponsive. A remote reboot did not finish, SSH briefly refused connections, and a forced power cycle restored management access.

After restart, `smartd` exited with status **17** when it found no monitorable devices. The USB disk enumerated later. Kernel logs then showed read I/O errors on `/dev/sda`, including sectors **136** and **2048**.

Those records did not identify which part of the USB storage path failed. The HDD, bridge, power supply and cable remain candidates; the link between the I/O errors and the stalled reboot is also unresolved.

### Mitigation

I removed the optional archive from active `fstab` configuration, disabled automatic SMART monitoring for that device, and excluded it from the Ansible preflight dependency checks. Management services continued to use eMMC and validated SD storage. The archive was no longer a prerequisite for service startup or a current backup destination.

A follow-up storage decision uses guards to check required mounts and Compose bind sources before starting stateful services. This prevents a missing SD mount from silently turning into an empty directory on the underlying filesystem.

### Open work

The USB drive and its connection still need isolated testing. Independent backup restoration is not established by this incident, and physical removal of the active SD card during writes has not been tested.

This record covers the R5C's USB archive. A separate SAS/HBA/expander investigation will need its own reviewed evidence before publication.
